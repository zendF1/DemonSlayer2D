# Phase 4b NPCs, Shops, Potions, Return Scroll and Carriage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** NPCs stand in the town and in every training camp. Players buy potions, return scrolls and protection charms for Xu, sell items for Xu, drink potions from the HUD (10 s cooldown per kind), return to town with a scroll, and pay the carriage driver to reach another camp. Forging (phase 3b/3c) now needs the Ubuyashiki blacksmith.

**Architecture:**
- Map files gain `town` and `npcs` (generated by `tools/mapgen.py`); `mapdata` validates them, `gamedata.Validate` cross-checks NPC shops against `items.json`.
- `item_stats.py` adds potions and the scroll as stackables with `sell` and `use`, sell prices for existing stackables and equipment, `use_cooldown_sec`, and two shops.
- `internal/items` gains pure helpers (sell value, use rules); the zone handles `BuyReq`, `SellReq`, `UseItemReq` and the blacksmith range; `World.Transfer` gains two kinds (`TransferScroll`, `TransferTravel`) whose departure checks consume a scroll or take Xu.
- Protocol 10: four request/response pairs (87–94, two of them answered with `EnterWorldResp`), three error codes.

**Tech stack:** Go, protobuf (buf), Python 3 scripts; Godot 4.7.2, GDScript, godobuf.

**Spec:** [docs/superpowers/specs/2026-11-20-giai-doan-4b-npc-cua-hang-binh-thuoc-design.md](../specs/2026-11-20-giai-doan-4b-npc-cua-hang-binh-thuoc-design.md). Section references below (§n) point to it.

**Prerequisite:** the [phase 4a plan](2026-11-20-giai-doan-4a-nhieu-map-cong-khu.md) is fully implemented (`World.Transfer`, `Departure`/`Departing`, `Cooldown` carry, protocol 9, `tools/mapgen.py`, `DevSetPlace`). Start from a server HEAD that contains it.

**Plan format (from the user):** interfaces, behaviour, test cases and TODOs only. Write the code at implementation time; nothing here is meant to be copied.

**Commit rules (from the user):** commit and push after every task with a clear message; **no** `Co-Authored-By` or other trailer; `git add` specific paths only (never `-a`), because other agents may edit the same tree; `git pull --rebase` before `git push`, never force push. Server tasks commit in this repo, client tasks in `../DemonSlayer2DGame`.

**Test rules:** Go tests with `-race` (DB/e2e: `TEST_DATABASE_URL='postgres://ds:ds@localhost:5433/ds_test?sslmode=disable' go test -race ./...`); 1–2 test files per package with `// ______________________TEST X_____________________` sections (GDScript `# ____...`); a fix comes with a test that fails on the old code; before committing Go: `staticcheck ./...`, `go vet ./...`, `graphify update .` (skip if graphify is missing). Every commit leaves `go build ./...` and `make test` green. Client: `tests/run.sh`.

**Environment:** never stop anything on :8099; the controller's acceptance server runs on :8199 (PID in the scratchpad file `gameserver-8199.pid`) — do not kill it; for your own live runs use another free port such as :8299 and kill only your PID. Never print DB passwords.

## Verified findings (2026-11-20, from the phase 3 and 4a specs; the code they describe is not written yet)

Everything this plan builds on lands in phases 3 and 4a. Find each symbol by name (`graphify explain "<symbol>"`) before editing, and read the 3a/3b/3c/4a plans' interfaces for the names.

- **Items (3a–3c):** `gamedata.Items` with `Stackables map[string]Stackable` and `StackOrder` (sort order = file order), `ParseItems` with strict decoding — the new `sell`/`use` fields must be added to the struct in the same task that regenerates `items.json`, or loading fails. `items.Inventory.Add` is all-or-nothing; `Discard(bagSlot, count)` removes from a slot; `items.Item` carries `Quality`, `Enhance`, `Gems`.
- **Zone item commands (3a–3c):** each command type is a `…Cmd` handled in `drain`, checks `DEAD` first, maps `items` errors to codes, saves at once with `z.saver.Save(z.state(p), nil)` and replies with `InventoryUpdate` + `SelfStats` built by the zone helpers (`inventoryUpdate`, `selfStats`). 3c keeps a per-player pending refine cleared by every item command except `PickupReq` and `RefineChooseReq` — this plan exempts `BuyReq` and `UseItemReq` (§1.2).
- **Forge checks (3b/3c):** `EnhanceReq`, `PunchReq`, `SocketReq`, `UnsocketReq`, `RefineReq` call the area's safe-zone test at step 2 and answer `NOT_IN_SAFE_ZONE` (find the shared helper; if each command calls `z.area.InSafe` itself, replace all five with one `z.nearRole(p, "blacksmith")`).
- **Transfers (4a):** `World.Transfer(ctx, m, TransferReq)` resolves the destination per `TransferKind`, `reserveIn`, then `zone.Depart` with a `Departure{Check, To, …}`; `Departing` exposes `Dead()`, `Pos()`, `ZoneChangeReady()`. Cooldowns cross zones as `PlayerInfo.Cooldowns map[string]time.Duration`.
- **Maps (4a):** `tools/mapgen.py` declares maps and self-checks; `mapdata.Parse` (strict) and `mapdata.Link` (cross-map) validate; real-map tests in `mapdata_test.go` run `--check`.
- **Client (3a–4a):** `core/item_book.gd`, `core/inventory.gd`, `core/pickup_loop.gd` (model for `npc_loop`), `core/forge_rules.gd` (`enhance_block(..., in_safe, ...)` etc.), `ui/forge_window.gd`, `ui/item_tooltip.gd`, `ui/hud.gd` potion buttons showing `LATER` (built in `_build_buttons`, `:297` before phase 3), `screens/world.gd` `_transfer(env)` (4a) for requests answered with `EnterWorldResp`.
