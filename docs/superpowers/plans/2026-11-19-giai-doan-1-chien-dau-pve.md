# Phase 1 PvE Combat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Players on `kumotori_1` fight wandering normal monsters with the default slash, gain EXP, level up, spend potential points, die and respawn in a safe zone, and heal at a rest point; two Godot clients see each other's hits.

**Architecture:** Monsters are zone entities next to players and share the AOI grid; the zone goroutine runs monster AI, attacks, deaths, timers and rest healing inside its tick. Formulas live in a pure `internal/combat` package. Map triggers (safe zones, rest points, camps) are new fields in the map JSON, and monster kinds and per-level stats are in `data/monsters.json`, generated by a balance script. Combat events ride in `WorldTick`, and the own character's stats come in a `SelfStats` push. The client keeps its Phase 0 split: Node-free logic in `core/` is tested headless, `ui/` draws in code, and `screens/world.gd` only wires the parts together.

**Tech stack:** Go 1.x, Postgres, goose migrations, protobuf (buf), coder/websocket; Godot 4.7.2, GDScript, godobuf.

**Spec:** [docs/superpowers/specs/2026-11-19-giai-doan-1-chien-dau-pve-design.md](../specs/2026-11-19-giai-doan-1-chien-dau-pve-design.md). Section references below (§n) point to it.

**Plan format (from the user):** this plan gives interfaces, behaviour, test cases and TODOs. Write the code at implementation time; nothing here is meant to be copied.

**Commit rules (from the user):** commit and push after every task; clear commit messages; **no** `Co-Authored-By` or other signature trailer. Server tasks commit in this repo, client tasks in `../DemonSlayer2DGame`.

**Test rules:** run Go tests with `-race`; keep 1–2 test files per package, with sections split by `// ______________________TEST X_____________________` (Go) or `# ______________________TEST X_____________________` (GDScript). After editing Go code and before committing, run `graphify update .`.

## Verified findings (2026-11-19)

- **Postgres accepts the column names `str`, `agi`, `vit` and `int` unquoted.** This was checked in `CREATE`, `INSERT`, `SELECT` and `UPDATE ... RETURNING` on the dev database. The names match game-design §3.3 of the server spec.
- **`exp_table.py` rounds with Python `round()`, which rounds half to even.** Go must use `math.RoundToEven(base*mult/10) * 10` to match `exp-table.csv`. The CSV has levels 1–89; level 90 has no next level.
- **The zone already owns the reply ordering for in-world requests.** `EnterWorldResp` is sent by the zone through the player's `Outbox` with the request seq. The new requests do the same: the gateway forwards `(seq, args)` to the zone, and the zone sends the reply or the `ErrorResp`. The gateway needs no reply channel.
- **Entity ids come from `world.nextEntity`**, an `atomic.Uint64`. Monster ids must come from the same counter, so the world passes `NewID func() uint64` to each zone.
- **The zone takes a `Grid` interface.** It never imports `mapdata`, and zone tests use a fake grid. Phase 1 keeps that: the world builds a `zone.Area` value from `mapdata` and `gamedata`, and zone tests build `Area` literals.
- **The proto message is `EntityMove`, not `Move`.** The spec calls it `Move`; the new field is `EntityMove.snap`.
- **Free field numbers:**
  - Envelope payload uses 2, 10–23, 30–33 and 40–42, so the new messages take 50–56.
  - `EntityEnter` uses 1–9, `EntityMove` 1–5, `WorldTick` 1–3 and `EnterWorldResp` 1–8.
  - `ErrorCode` ends at 15.
- **GDScript-safe names:** none of `Hit`, `Death`, `HpChange`, `LevelUp`, `SelfStats`, `strength`, `agility`, `vitality`, `intellect` or `snap` clashes with a GDScript keyword, built-in class or `Object` method.
- **The client's `tools/sync_server.sh` copies `server/maps` to `data/maps`.** The client does not need `data/monsters.json`.

### Task 3: Server — map triggers

**Files:** `internal/mapdata/mapdata.go`, `internal/mapdata/mapdata_test.go`, `maps/kumotori_1.json`.

Interface additions:
- Types:
  - `type Rect struct{ ID string; X, Y, W, H int }`, with `func (r Rect) ContainsTile(tx, ty int) bool` (rule in §2.1).
  - `type RestPoint struct{ ID string; X, Y, Radius float32 }`
  - `type Camp struct{ ID, Monster string; X, Y, Radius float32; Count, MinLevel, MaxLevel int }`
- `Map` gains `SafeZones []Rect`, `RestPoints []RestPoint`, `Camps []Camp`.
- Methods:

- JSON fields: `safe_zones`, `rest_points`, `camps` (all optional, so maps without them stay valid).

Validation (§2.1): `Parse` returns an error naming the map and the bad item when any of these fails:
- a safe zone lies outside the map, or has non-positive `w` or `h`;

- spawn `default` lies outside the safe zones, when the map has any;
- for a camp:
  - `min_level > max_level`, `count ≤ 0` or `radius ≤ 0`;
  - fewer than `count` camp tiles;
  - any camp tile in a safe zone;
- an `id` is duplicated within a list.

Monster ids are checked against `gamedata` in Task 4, not here.

### Task 4: Server — monster data

**Files:** `docs/balance/monster_stats.py`, `data/monsters.json`, `internal/gamedata/gamedata.go`, `internal/gamedata/gamedata_test.go`, `internal/config/config.go` (+ test), `internal/app/app.go`.

- The rules come from §2.3:
  - reference Viêm, no gear;
  - `10 × (L − 1)` points, with floor(2/3) of them in STR and the rest in VIT;
  - monster defense 8L;
  - HP = 4 slashes;
  - attack = ceil(0.04 × HP_ref / (1 − def_ref / (def_ref + 20L))).
- Levels 1–5 are written. The kinds are kept in the script as data, so the JSON is fully generated.
- Asserts:
  - each monster hit lands within 3.9–4.1% of the reference HP;
  - the level-10 attack is 95 (cross-check with game-design §5.9).
- The printed table equals §2.3.

### Task 7: Server — monster aggro, chase, attack and leash

**Files:** `internal/zone/monster.go`, `internal/zone/combat.go` (new: player damage and death), `internal/zone/zone.go`, `internal/zone/combat_test.go` (new).

Behaviour (§4.2, §3.6):
- **Valid player for a monster:** alive, not in a safe zone, in this zone.
- **`idle`:**
  - The nearest valid player within `Kind.AggroRange` becomes the target, and the state becomes `chase`.
  - Only entities in the 3×3 AOI cells around the monster are scanned.
- **`chase`:**
  - Direction = normalised (target.pos − pos).
  - Step at `Kind.Speed × cfg.MoveSpeed / TickRate` with `monsterGrid()`.
  - Stop moving when within 1.3 tiles. The state becomes `attack` when within `Kind.AttackRange`.
- **`attack`:**
  - When `tickNo ≥ nextAttack`: damage = `combat.Damage(level.Attack, target.PhysDefense, monster level)`, then record a `Hit` event and set `nextAttack = tickNo + ticks(AttackSec)`.
  - If the target goes beyond `AttackRange`, go back to `chase`.
- **Leash:** in `chase` or `attack`, when `dist(pos, home) > Kind.LeashRange`, switch to `returning`:

**Files:** `internal/zone/combat.go`, `internal/zone/spawn.go`, `internal/zone/zone.go`, `internal/zone/combat_test.go`, `internal/world/world.go`.

Interface:

- Join:
  - computes `stats` with `classes.IsMagic(info.Class)`;
  - HP/MP of -1 means full; values above max are clamped;

- `func (z *Zone) Attack(id uint64, seq uint32, target uint64) bool` enqueues `attackCmd` and returns false when the inbox is full. `Membership.Attack(seq, target) bool` is added in `world`.
- In `drain`, an `attackCmd` is stored as the player's `pendingAttack`. A newer one in the same tick replaces the old one, and the old one is answered `ON_COOLDOWN`.
- `func (z *Zone) resolveAttacks()` runs at step 2. It goes through players in id order and checks each pending attack in the order of §5.1:
  1. `DEAD`
  2. `IN_SAFE_ZONE`
  3. `INVALID_TARGET` (missing, not a monster, dead, or `returning`)
  4. `OUT_OF_RANGE`: distance > `combat.SlashRange + attackRangeSlack` (0.5), or `lineBlocked(a, b)`

  - send `AttackResp` with the seq, immediately;
  - damage = `combat.Damage(combat.SlashBase(stats), level.Defense, player level)`;
  - record a `Hit`;
  - add the player to the monster's `attackers`;
  - an idle monster targets the attacker and starts `chase`.
- `func lineBlocked(g Grid, a, b Vec2) bool` samples the segment every 0.25 tiles and reports any blocked tile. It ignores the endpoints' own tiles.
- Monster death:
  - `dead = true`, `dir = 0`, `diedAt = tickNo`;
  - record `Death`;
  - append `diedAt + ticks(Kind.RespawnSec)` to the camp's `pending`.
  - The killer gets `combat.MonsterExp(level)`:
    - via `combat.GainExp`;
    - +`PointsPerLevel` × levels gained to `freePoints`;
    - recompute `stats`;
    - full HP/MP on a level-up;
    - record a `LevelUp` and an `HpChange`;
    - **save immediately** with `z.saver.Save(z.state(p), nil)`;
    - `statsDirty = true`, also when only EXP changed.
- Timers in `spawn.go`, at step 5:
  - a dead monster with `tickNo ≥ diedAt + ticks(1.0)` is removed from cells and maps, so viewers get `EntityLeave` through `syncView`;
  - a camp with a due `pending` tick spawns a new monster.
- After `WorldTick`, `syncView` sends a `SelfStats` push (seq 0) to each player with `statsDirty`, then clears the flag.
- `z.state(p)` includes points, free points, hp and mp.

### Task 19: Client — world wiring

**Files:** `screens/world.gd`, `autoload/config.gd`. These are checked by the smoke test and by playing (Task 20).

Behaviour:
- **Input actions in `Config`:** `attack` (Space), `switch_target` (Tab), `stats` (C).
- **Entity table** in world: `id → {kind, name, level, hp, max_hp, dead, view}`.
  - It is filled from `EntityEnter` (hp, max_hp, dead, kind, level) and updated from `Hit`, `Death`, `HpChange` and `LevelUp`.
  - Candidates for `Targeting` are monsters with `dead == false`, at their interpolated positions.
- **Each frame:**
  1. Read the manual direction (keys or joystick).
  2. Run `Targeting.update` with the own position and `grid.in_safe_zone`.
  3. Run `AttackLoop.step(now, pos, target pos, attack held, manual)`.
  4. The local tick uses the manual direction when it is non-zero, otherwise the loop's `dir`, and zero while dead.
  5. When `attack` is true, send `AttackReq` through `Net.request` and pass the reply code to `AttackLoop.on_reply`:
     - `drop_target` → `Targeting.select(0)`;
     - `notice` → HUD notice text.
  6. Update the rest ring with `RestTimer.update`.
- **Pressing attack with no target** runs `Targeting.nearest`. If that finds none, the HUD shows "Không có mục tiêu" once per press.
- **Clicking or tapping a monster** in world space selects it: use the nearest monster within 0.6 tiles of the click. Clicking the ground or dragging the joystick does nothing.
- **`WorldTick` handling** (after moves, as today):
  - `hits`:
    - update hp;
    - spawn `damage_text` over the target, with `hurt_self` when the target is self;
    - spawn `slash_effect` from the attacker;
    - self target → `hud.set_hp`;
  - `deaths`:
    - mark dead;
    - a monster's view gets `fade_out()`;
    - if the target died → `Targeting.on_death`;
    - self died → `death_panel.open()`, `AttackLoop.reset()`;
  - `hp_changes`: set hp/max_hp, and the HUD when self;
  - `level_ups`: update the label, show small "Lên cấp" over others.
  - `EntityMove` with `snap` → `Interpolator.add(..., true)`.
- **`SelfStats`:**
  - comes from `EnterWorldResp.stats` at start, then from `SelfStats` pushes and `AllocatePointsResp`;
  - calls `hud.set_self`;
  - a level higher than the last one → `hud.show_level_up`.
- **Respawn:**
  - `death_panel.respawn_pressed` → `RespawnReq`;
  - on `RespawnResp`: `Predictor.reset(Vector2(x, y))`, close the panel, mark alive.
  - After the server's 60 s auto-respawn no reply comes. The client detects it by an own `EntityMove` with `snap` while dead, and does the same three steps at that position.
- **Stats panel:**
  - `stats` action/button → `stats_panel.open(last stats)`;
  - `confirmed` → `AllocatePointsReq`;
  - the reply's stats → `hud.set_self` and refresh the panel; errors show as notice text.
- `world.gd` stays wiring only: no formulas, and no targeting or loop logic inline.
